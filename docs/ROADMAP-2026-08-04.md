## Phase 1 — The Page paginates

**Rationale.** It is the largest unlock available and the only item on the list
that other work is explicitly waiting behind.

**1.1 — Pagination**, per `docs/vision/PAGE-MODE-SPEC.md`. Page Mode was always
intended to paginate; the current Page is one continuous column, which is also
why the whole reading's overhead lands at once instead of in divisible chunks.

**1.2 — Turn on procedural figures.** Already built and tested —
`pageCollectionId` and `sampleWorkEngine` in `work-engines.js`, the Chamber's
resolver branch — and held behind one constant, `PROCEDURAL_FIGURES` in
`flow.js`. Per `EXPERIENCE-PROGRAM-SPEC.md` §12 this was deferred *specifically
until the Page paginates*, so it lands here and costs almost nothing.

**This is the Journey's remaining Page gap.** A Journey's *museum* works already
reach the page — that fix landed. What a Journey's page still lacks is its
PROCEDURAL imagery, which is this item and not a separate one. Worth stating
because "Journey Page Mode support" reads like a whole feature and is in fact
one constant behind one dependency.

**1.3 — Projection is not carried through persistence** (red-team #11). A
restored session forgets whether it was a page or a stream.

**1.4 — Print output depends on scroll position** (red-team #12). Figures
hydrate lazily via `IntersectionObserver` in `PageReader.js`, so printing before
scrolling omits every figure never brought into view. Any fix must force-hydrate
before print. Note for whoever writes the test: this same property is why a test
counting `.page-figure img` must scroll first or it undercounts — it has already
cost real debugging time once.

**Not in this phase:** the Journey's Page support, which **already landed**. The
Page now reads a Journey's authored program; the Homeric movement's museum works
reach the page.

## Phase 1b — Page Mode: the comprehensive pass *(new, 2026-08-04)*

> **DONE, 2026-08-04.** All four items landed. The unit suite is green and
> `e2e/page-typography.spec.js` verifies the results in a real browser.

Requested after reading real pages. Pagination shipped and then accumulated
fixes fast enough that the rules began contradicting each other; this is the
pass that makes them one system rather than a pile.

**1b.1 — The known gap. SOLVED, and it was not a rule at all.** An inline
`CHAPTER II` did not open a page. `opensAChapter` was reached, its inputs were
correct, and it still returned false — because the word boundary in its regex
had been written to disk as a **literal BACKSPACE (U+0008)** instead of the two
characters backslash-b, so the pattern demanded a control character after
"chapter". The byte is invisible in an editor, in `git diff`, and in every file
dump used to hunt it; two sessions of reasoning about rule ordering found
nothing because there was nothing there to find. It was located by printing char
codes.

A standing guard now sweeps every source file for control characters
(`src/core/source-hygiene.test.js`), because a defect nobody can *see* is worth
one cheap check per run. It was the only occurrence in the repository.

**1b.2 — Rule conflicts, resolved deliberately. DONE.** The corrective passes
now have a stated precedence rather than an accidental order — **structure
outranks balance, balance runs last and may not violate structure** — written
into `paginator.js` where the passes are. Three real conflicts were found and
each has a test:

- the balance pass buried a chapter opening under borrowed prose;
- the heading pass could strand a page holding a single item;
- the balance pass's own cascade walked a thin page from the tail of a reading
  **all the way to page one**, where the reader meets it first. The existing R4
  test inspected only the LAST page and watched it stroll past.

Where a loan would merely relocate the fault, the thin page is now absorbed
upward within a tolerance the frame already allows.

**1b.3 — Elongate. DONE, and the fault was worse than "not findable".** The
control *hid itself* once pressed: `PageReader` reported four positional
arguments and the Chamber took the first two, inferring the rest from `total` —
and an elongated reading is ONE page, which reads as "nothing to paginate". The
report is one **object** now, so a field cannot be dropped the way a trailing
argument can. Elongating also **keeps the reader's place** in both directions,
anchored on an item rather than an offset.

**1b.4 — Verify against readings, not fixtures. DONE.** Two heading fixes passed
unit tests written to match my own model of the fault while the page stayed
visibly wrong. The instrument that found it is now
`e2e/page-typography.spec.js`: it walks the real pages and asks a question about
GEOMETRY — is a figure sitting level with a title while standing off to one side
of it — which is the signature of a float that has wrapped a heading. It also
verifies the chapter opening and the Elongate round trip in a browser.

## Phase 1c — Reading onward *(new, 2026-08-04)*

**A gap in the UI model, not a bug.** A reader who finishes a chapter cannot
advance to the next without returning to the Chamber. The Page is a projection
of a session, and the session is one reading — so "next chapter" is not a Page
control at all: it must move the STREAM's position too, or the two projections
disagree about where the reader is, which is the one thing this architecture
exists to prevent.

That makes it a session-level act with a Page affordance, not a page-turn. Worth
its own design pass; noted here so it is not rediscovered.

## Phase 2 — The Stream's seams

Two boundary behaviours: what the imagery does when the reader stops, and what
the reading shows when one work ends and another begins.

### 2.1 — The Gallery pause boundary

**Correction, 2026-08-04.** This was filed under "Page Mode open threads" and it
is a **Stream** question — Gallery is a continuous field behind the reading
stream. It appeared in the Page notes only because it surfaced during that
hardening pass.

**The rule is decided:** an authored program **pins** the imagery to the
reading, an unauthored pool does not. So pausing halts the gallery when a
`visualProgram` is driving it — otherwise the imagery plays ahead of the text
and then runs out of hydration — and lets it drift for procedural and general
collections, where it is ambient and has no claim on any particular passage.

This is the same bound/unbound distinction `cueForAtom` already encodes, which
is the argument for it: no new vocabulary, one existing question asked in one
more place.

Small, decided, and it closes a deferral rather than opening one.

### 2.2 — The intermission between movements

*New, Mateo, 2026-08-04.* When a Journey's movement ends, hold a brief
intermission — smooth transitions, and the title and details of the work coming
next.

**It has a home already, which is the argument for building it now.** Three
pieces exist and none of them were built for this:

- A **boundary is an atom**, not a timer (`journey-schedulers.js`). "The
  transition IS the current atom, so pausing a Journey pauses its transitions
  for free, and no controller can drift from the state." An intermission built
  on this inherits pause, resume, scrub and shuttle without writing any of them.
- The canonical Experience Program already carries **transition** as an
  independent track beside movement, visual, audio-bed and swell. The
  intermission is that track becoming visible; it is not a new concept.
- The audio schedule already **fades to silence at a V1 boundary**. So the seam
  is currently full of nothing in both channels — the intermission fills one of
  them and deliberately leaves the other empty.

**It revises a decision that was made on purpose,** and that should be done with
open eyes rather than by overwriting a comment. `Chamber.onMovementChange`
currently handles `kind: 'boundary'` by announcing *nothing*, and says why: *"A
transition announces nothing. It is the silence between two worlds, and naming
it would be talking over it."*

That reasoning still holds for naming **the transition**. It does not hold for
naming **what is arriving** — the difference between captioning a silence and
using it to introduce the next work. The build should keep the first prohibition
and take the second liberty, and the comment should be rewritten to say so.

**The three-layer law decides the content.** Per `JOURNEYS-SPEC` §5 the Chamber
receives a label and an identity, never a meaning: it must not compose the
intermission. The **Journey authors** what the card says, the runtime schedules
it on the boundary atom, the Chamber renders what it is handed. Movements
already carry the material — the credits line the Journeys view shows ("The
Storm of Steel — Chatto & Windus, London, 1929; Basil Creighton translation") is
authored per movement and is exactly the "details" being asked for.

**Design constraints, so it stays a threshold and not a splash screen:**

- **Duration is authored, not hard-coded.** The boundary atom's own duration
  governs the hold, so "brief" is a compositional decision per Journey.
- **Reverent degradation.** No credits → title alone. No title → today's
  silence, unchanged. The intermission never becomes a broken frame.
- **Reduced motion.** The crossfade is a state change, not an animation.
- **The phone.** It renders inside the reading band's grammar — the same
  stratum, not a new full-screen surface.
- **Silence stays silent.** The audio bed's existing fade at a boundary is not
  disturbed; the intermission is visual only.

**Sequenced after 2.1** because 2.1 is decided and small, and because both
touch what happens at a boundary — doing them together means reading that code
once.

Worth its own short spec section before building. It is the first thing in a
while that adds a *surface* rather than correcting one.

## Phase 0.4 — the canonical boundary, end to end *(external review, verified)*

An outside review of `0fb9c2b` raised five findings. **I checked all five
against the code rather than accepting them, and all five are real.** That is a
good review. Two corrections to its framing are noted below.

| # | finding | verified | state |
|---|---|---|---|
| 5 | a named swell substitutes a random one | `engine.js:1156` | **FIXED 2026-08-05** |
| 2 | Workshop and Session limits disagree | 4,194,304 vs 2,000,000 | open |
| 3 | accepted media cannot be stored | 8 MB → data URI → `localStorage` | open |
| 4 | canonical validation permits same-lane overlap | no `overlap` in `experience-program.js` | open |
| 1 | War's coda never executes | `handoff.test.js` "drops the coda" | open, **by decision** |

### 5 — fixed, because it broke a standing law

`playSwell('funeral-bell')` with nothing by that name warned and then played a
**random different swell**. The score asks for a funeral bell; the runtime
sounds a rising cosmic swell, and nothing says so.

That is not graceful degradation, it is **false execution**, and it violates the
rule the imagery has followed from the beginning: *a work that will not resolve
is absent, never a substitute.* Silence is a valid scored state; the wrong sound
is not. A named request now fails closed. An unnamed one — *"give me a swell"* —
is a different request and still takes any of them.

The test observes whether a buffer source was **created**. A throwing stub
proves nothing here: `playSwell` wraps its body in try/catch and swallows it.

### 2, 3, 4 — open, and the review understates 3

**2.** `workshop-project.js` allows 4,194,304 characters per source;
`session-compiler.js` allows 2,000,000 per source *and* in total. A project
validates, saves, reopens — and fails only at Run. One shared limits authority,
and an invariant: *every valid Workshop project compiles.*

**3.** Worse than stated. An 8 MB image becomes a data URI, which base64
inflates by about a third — roughly 10.7 MB — and the whole project is then
`JSON.stringify`d into `localStorage`, whose typical ceiling is 5–10 MB for
*everything*. **A single accepted image cannot be saved at all.** This is a hard
prerequisite for MP4, not a parallel concern.

**4.** Confirmed: `experience-program.js` contains no overlap check. The rule
lives in the editor adapters alone — which is this codebase's oldest failure
shape, a vocabulary in two places where only one copy is maintained. Array
order must not become an accidental layer system. **The JSON import boundary
should not open until this is canonical.**

### 1 — real as a product gap, but it is a DECISION, not an oversight

The review reads it as a defect. The test is named *"drops the coda, which joins
nothing"* and says why: *"A transition after the final movement is a scored
ending. It stays in the movement program for reporting and has no atom, because
there is no break for it to replace."* That is the review's own option 2,
chosen deliberately.

**Its argument for option 1 is still the better one.** War ends in an emptied
landscape and silence, and authors seven seconds of exactly that. A Journey
should finish in its authored silence. Worth revisiting on those grounds — not
as a bug report.

### Where the review is overtaken

It predates this session's work. Page Mode **is** paginated, Phase 0 is complete,
and 3.4 does not gate the Chain (below). Its sequencing advice — durable asset
storage before MP4, canonical overlap validation before JSON import — stands.

## Phase 4 prerequisites — re-examined 2026-08-05

**3.4 does not gate RISE Chain, and the argument is in the build order itself.**

`EXPERIENCE-PROGRAM-SPEC` step 9 specifies the Chain as *"a research mode —
sandbox, **one visual engine, one soundscape**, before any Journey
integration."* §6's engine registry scope solves a **browsing and visibility**
problem: keeping "Michael's Flaming Sword" out of a menu beside "Fractal Flame"
without a second allowlist. **One engine means no menu to filter.** The
taxonomy is real work and it belongs to the Workshop and the Live Curator, not
to a sandbox that instantiates a single engine by name.

Dropped from the critical path. Phase 4 is gated on nothing in Phase 3.

### What the Chain actually needs, read off its own §9

```
generated phrase → shifts visual dynamics → changes acoustic state
    → alters transition probabilities → conditions the next phrase
```

Four coupled processes. So the question is not "what taxonomy do we have" but
**"can each layer be driven, continuously, at runtime?"** Measured:

| layer | surface today | ready? |
|---|---|---|
| visual | `generate(signal, seed, options)` and `step(dt, signal)` — every engine takes a **`signal`** on every frame | **yes** |
| audio | `createSoundscape(id) → { start, stop }` | **no — binary** |

The visual half is already built and the parameter is even named `signal`,
which is the right word for it. A soundscape has no equivalent: it is on or
off, and there is no way to say *more agitated*.

### On binding audio to the Experience Program

Mateo's instinct — that the audio layer is the missing piece — is right in
substance, and the fix is not the one it sounds like.

**Binding audio to the Experience Program is already done.** Build-order step 4,
"the audio lane and sync groups", landed 2026-08-04: independent bed/event
lowering and execution, tone cues, sync-group preservation, transport
cancellation.

**And it is the wrong instrument for this anyway.** The Experience Program is a
*canonical authored score* — compiled ahead of time, immutable, never
second-guessed. The Chain is generative **at runtime**. A score written in
advance cannot express *"the acoustic state changed because of the phrase just
generated"*, because that phrase did not exist when the score was written. A
better score does not help; the Chain needs the thing a score deliberately is
not.

### The one real prerequisite, and it is small

**Give one soundscape a parameter surface**, matching what visual engines
already have — `{ start, stop, signal(state) }` or equivalent. One soundscape,
because that is what step 9 asks for.

That is the whole gate. It is smaller than 3.4 and it is the sandbox's own
first component rather than a dependency in front of it.

## Phase 4 — RISE Chain

Step 9, per the spec: a **research mode** — sandboxed, one visual engine.

### 4.1 — The text lane — **STATUS: SHIPPED (sandbox), 2026-08-05**

Not wired into the Chamber and not meant to be yet. `src/chain/markov.js`
+ `scripts/chain-sandbox.mjs` + `scripts/chain-profiles.mjs`, 21 unit
tests. What exists: variable-order chain over the whole shelf, entropy
backoff, token-level verbatim ceiling, seeded replay, per-transition
genealogy, selection profiles, and the `bias` hook the coupled organism
will reach through.

**Open in this lane:** per-step modulation of `tail:k` (the natural
bridge to the visual lane), sentence-boundary awareness so a dream ends
on a full stop, and the Chamber surface itself. Parked deliberately —
§9's other two lanes come first, and audio wants its own day.

`src/chain/markov.js` — a variable-order Markov chain over the Archive,
with `scripts/chain-sandbox.mjs` to hear it. Text only: no visuals, no
audio, nothing wired into the Chamber. Audio is deliberately deferred to
its own day of engineering, per Mateo — the Chain's sound wants to be a
live instrument the chain is playing, not a soundscape it triggers.

**The one design decision worth carrying forward.** A fixed order-3 chain
does not *sometimes* quote; it quotes whenever its context is
deterministic, and in natural text most trigrams have exactly one
continuation. Raising the order makes it strictly worse — at order 5 the
chain is a photocopier. So the model measures the **entropy** of the
context it stands in and backs off to a shorter one when the
distribution collapses. §9's law and information theory turn out to be
the same constraint: *a deterministic context carries no information, and
following it is transcription rather than composition.* It is therefore
implemented once, in the sampler, rather than as a filter afterwards.

A hard ceiling backs it up, and it is a constraint on the TOKEN rather
than on the order — the first attempt backed off to a shorter context,
which bounds nothing, because order 0 is unguarded by construction.

**Measured over the whole shelf:** 88 works, 830,887 tokens, order 3.
Longest single-work run 3–5 tokens; genealogy diffuse, no work above 7%.
The property is worth naming: **the more of the Archive it dreams over,
the less any one book owns a sentence,** and the verbatim guard barely
has to fire.

**Next in this lane:** the `bias` hook already exists — `(token, context)
→ multiplier` — which is where §9's coupled organism will reach in. The
visual lane conditions the text by reweighting transitions, never by
editing output.

**Gated on nothing in Phase 3.** This paragraph used to say "gated only on step
7 (3.4)" and that is wrong; see *Phase 4 prerequisites* above for the argument,
which comes from the build order itself. The one real prerequisite is a
**parameter surface on one soundscape**, and that is the sandbox's own first
component rather than a dependency in front of it.

### 7.2 — Sentence mode, and where the offline model earns its place

**Found by asking whether phrase mode had collapsed into sentence mode.**
It had not — measured as cut-point *purity*, the share of phrase
boundaries that are merely sentence boundaries, phrase mode became MORE
distinct (41.4% → 39.2%), and the shift was concentrated where the new
mechanics act (−3.2pp in paragraphs carrying `?` or `(`, −0.5pp
elsewhere).

But the reason it diverged is the finding: **sentence mode is not
cutting at those questions either.** It still requires
`[.!?]` + whitespace + CAPITAL, and this translation continues in lower
case — *"…to do me hurt? for what profit…"*. Nine such questions in
Meditations VI alone.

**Two defects, and they want different instruments.** Counted over
11,467 sentence-mode atoms from eight works:

| defect | count | fixable by |
|---|---|---|
| a `?`/`!` whose sentence continues in lower case | **61** | one line — no abbreviation ends in `?` |
| a split *after* an abbreviation (`Mr.`, `St.`, `i.e.`) | **237** | not a regex |

The false splits concentrate exactly where a reader would notice:
**Middlemarch 140, Pride and Prejudice 87** — `Mr. Casaubon` and
`Mrs. Bennet` cut in half, mid-name, on every occurrence. The capital
guard is doing abbreviation duty and doing it badly, and the fix is not
a longer abbreviation list: that list is unbounded and edition-specific.

**THIS is the task the offline model is actually for.** The awareness
study (§4) drew the line already and it holds up:

> *Clause segmentation is a parser, not a model.*

Sentence-boundary detection is the opposite case — **Punkt is literally
trained for this one job**, unsupervised, per-corpus, and it learns a
work's own abbreviations rather than being handed a list. spaCy and
stanza carry equivalents. This is the ML application with a real target.

**The hard constraint is unchanged and it decides the architecture.**
Atom boundaries are what visual programs anchor to, so a reading must be
the same reading twice. That rules out inference at read time and rules
IN what the Archive already does: derive offline, commit the artifact,
ship it. `division-index.json` is the precedent — 91 works of structure
derived once by a script and consumed by a runtime that never re-derives
it. A `sentence-index` alongside it would be the same shape.

**Order, and why:**

1. **The one-line fix first** — `?` and `!` need no capital guard, 61
   measured cases, and it can ship in an hour with the same before/after
   methodology used for 7.1. Blast radius is real though: Journeys and
   the Atrium compile at sentence level, and the Atrium pins
   compiler-derived durations, so expect the pins to move again.
2. **Then the ingest artifact** for the 237. It is a build-step, a
   committed index, and a consumer — three pieces, none of them
   speculative, and the payoff is a class of defect no constant can
   reach.

### 7.3 — The parser, for the interrupted subject

Unchanged and still open. The *interrupted subject* — 35 instances in
Book VI — did not move under 7.1 at all, exactly as the awareness study
predicted: the floor reasons about LENGTH and the defect is about
GRAMMATICAL ROLE, and punctuation cannot reach it either.

Distinct from 7.2 and worth keeping distinct: **7.2 asks where a
sentence ends, 7.3 asks what a sentence is made of.** The first is
solved by a trained boundary detector; the second needs a dependency
parse. Both run at ingest; only the second is the "parser, not a model"
the study meant.

**A verified defect, not a refinement.** `splitPhrases` splits on
`, ; : — – |` and on `.` followed by a capital. **`?` and `!` are absent
from both alternatives**, while `splitSentences` has `[.!?]` — so PHRASE
mode, the finer mode, is coarser than SENTENCE mode at a question:

```
"Who goes there? He asked again. Nobody answered."
  phrase   → ["Who goes there? He asked again.", "Nobody answered."]
  sentence → ["Who goes there?", "He asked again.", "Nobody answered."]
```

A question is the most emphatic boundary in prose and phrase mode reads
straight through it. Parenthetical clauses are never split either.

**Why this before the other open items:** it touches every reading in
the app, it is bounded, and the two prior studies
(`PHRASE-CHUNKING-STUDY`, `CHUNKER-AWARENESS-STUDY`) already establish
the measurement methodology — fragment rate, stutter runs, interrupted
subjects — so the change can be measured rather than judged by eye.

**Care required, per those studies:**
- The floor (`applyPhraseFloor`) must not merge across a `?` or `!` any
  more than it merges across a `.` — refusal #2 there covers sentence
  ends and needs to learn these.
- `!` inside a clause is not always a boundary: *"What is truth! said
  jesting Pilate"* is one utterance. Splitting after `!` unconditionally
  would fragment dialogue that sentence mode keeps whole.
- Authored `|` still wins over everything.

**Then, and only then, the ML question** (§4 of the awareness study): a
pretrained parser at ingest time, offline, deterministic. The study's own
conclusion stands — *clause segmentation is a parser, not a model*, and
determinism is a hard constraint because visual programs anchor to atom
boundaries.

## Phase 5 — The Solarium, narrowed

*From a product review, 2026-08-04. Summarised here; the review is the
authority on the editorial judgements of individual sequences.*

**The verdict is not to retire the Solarium. It is to narrow what it is for.**

> Keep the Solarium as RISE's temporal orchestration layer.
> Stop treating it as a separate, endlessly expanding content universe.

It answers a question nothing else in the product answers. The Chamber answers
*what do I want to read*; Journeys answer *what authored transformation do I
want to enter*; the Solarium answers **what belongs to this moment of my life**.
That relationship to lived time is genuinely unique here — most software is
temporally indifferent and serves the same thing at 7am and midnight.

### The architectural move

> **The Solarium should schedule programs, not define another species of
> program.**

It needs to contribute only:

```js
{ temporalWindow: 'evening', programId: 'inner-citadel', recurrence: 'daily' }
```

Its canonical temporal sequences become first-party Experience Programs like any
other, launchable from the Workshop, Vault, a Journey or the Chamber.

**This is why it belongs on this roadmap and not an earlier one.** The move was
expensive while the Solarium needed its own sequence format and content
pipeline; it is cheap now that `rise.experience-program.v1` is canonical and
strict. Phases 3.2 and 3.3 make the scheduled thing portable, so this lands
naturally after them.

### Keep

The doorway, the solar dial and live time context, the seven windows,
"aligned with this hour", **My Day**, assigning saved user compositions to
windows, and a small set of polished first-party temporal practices.

My Day is the most valuable part and the least developed: a window bound to a
SOL sequence *or* a Workshop blueprint *or* an Experience Program turns the
Solarium into a **recurrence and ritual system** rather than another shelf.

### Migrate

The taxonomy is three products wearing one name — seven Temporal, five
Situational, four Archetypal — and only the first is native to a solar day.

- **Temporal** stays. It is the clearest reason the feature exists, and it forms
  an actual diurnal cycle rather than a list of exercises. Edit the language to
  be more spacious and less uniformly motivational.
- **Situational** moves out of the central taxonomy into Practices or Vault
  compositions. Still schedulable through My Day.
- **Archetypal** is where the largest reduction belongs: rewrite as explicitly
  authored poetic compositions, or retire individually.
- The full catalog browser becomes **secondary** to the current recommendation
  and the personal day plan.

### Editorial review, before any of it is re-published

Four named concerns, and they matter more here than the refactor does — this is
the product speaking in its own declarative voice:

- **Microcosmic Body** blurs metaphor, spiritual reading and scientific claim
  (one spiral in galaxies, shells, storms and the cochlea; flesh and cosmos as
  "one thing"). Beautiful as poetry; as instruction it reads as unsupported
  cosmology. Either the voice changes or the claims do.
- **Cosmological Motivation** moves from scale to existential conclusion too
  fast, and carries figures that would need re-verifying as estimates change.
- **Historical Warrior** risks converting historically specific suffering into a
  general endurance metaphor.
- **Grief Space** and **After the Storm** are sensitively written, but a
  general-purpose application should be careful about implying one authored
  script answers every grief, or about drifting into a quasi-counselling role.

### The formulation worth keeping

> The Chamber is where an experience occurs.
> The Workshop is where it is composed.
> The Vault is where it is preserved.
> Journeys are where authored works are published.
> **The Solarium is when they return.**

### Stop, effective immediately

Costs nothing and can be adopted before any code moves: stop expanding the
Solarium as a parallel library of generic guided scripts, stop treating the
three categories as equally native, and stop giving every human condition a
RISE-authored motivational response.

## Phase 8 — The Vertically Responsive Text Band *(Mateo, 2026-08-06)*

**The report.** On a phone, in a Journey, the reading text sits over the
centre of the screen — which is exactly where the visualisers put their
subject. The two are fighting for the same pixels and the text wins,
because it must.

**The proposal, as given:** make the band's y-position **programmable**
(desktop and mobile), and let a reader **drag it up or down**.

**Why it is not just a CSS offset.** The band is centred by flexbox —
`.chamber-field` is `flex: 1` with `align-items: center` — so the
mechanism is one transform. Everything expensive is around it:

- **Programmable means authored**, and authored means the three-layer law
  applies: a content domain sets the band, the runtime follows, the cortex
  renders. That is a field on the Experience Program, not a preference —
  and a Journey that positions its band is making the same kind of
  statement as one that positions its imagery.
- **A reader's drag must not overrule an authored band silently**, nor be
  forgotten the moment they do it. This is the same ownership question the
  `visualProgram` persistence bug turned out to be: text identity vs
  preference. Decide which one the band is BEFORE building it.
- **The gesture has to be disambiguated from advancing the reading.** The
  Chamber's field responds to input already; a drag that starts as a tap
  is the hard part, not the transform.
- **Page Mode has no band** — it has a column. The setting should either
  be projection-scoped or say plainly that it governs the stream only.

**Worth noting it is a mobile fix with a desktop life.** Even on a wide
screen, a reader who wants the imagery uncovered has no way to ask.

## Phase 6 — The Atrium on a phone *(Mateo, 2026-08-05)*

**The Atrium needs heavy UI optimisation on mobile.** Sequenced beside the
Solarium because both are surfaces the mobile density pass never reached, and
because doing them together means measuring the phone once.

**It is the least mobile-adapted surface in the app, and the numbers say so:**

| surface | media rules | lines | mobile pass? |
|---|---|---|---|
| Chamber | 9 | 1,370 | yes, 2026-08-04 |
| Portal | 7 | 1,420 | yes |
| Library | 5 | 915 | partial |
| **Atrium** | **3** | 1,233 | **no** |

**And its layout is the hard case, not a spacing problem.** The Atrium places
works at computed absolute coordinates on a horizontal era timeline —
`x: 42 + eraIndex * 250, y: 72 + row * 92`. That geometry assumes a desktop
canvas; on a 390px viewport an era is two thirds of a screen wide and the
timeline is a scroll the reader cannot see the shape of. **Tightening the CSS
will not fix a coordinate system.** The question to answer first is what the
Atrium *is* on a phone — the same timeline scrolled, or a different projection
of the same collection, in the way the Page is a projection of the Stream.

**Method, per the mobile pass that worked:** measure before changing anything.
That pass moved the Vault from 1 archetype visible to 5, the Library from 0
books on first screen to 1, and the Audio panel from 1,273px to 919px — by
counting what reached the first viewport, not by judging screenshots. The
standing note in *Parked* applies in reverse here too: **the desktop numbers do
not transfer.**

**Constraint, unchanged:** `aic-*` category ids stay untouched, and the Atrium
is curation-only — every image is a work someone chose. A density pass may
change what is shown first; it may not change what is shown.

## A property worth knowing before the next session

**A reading's text is persisted when it is chosen, not derived when it is
read.** So a fix to how divisions are cut does not reach a reading already in
hand — a hard reload will not do it; the text has to be cleared and re-added.
That cost real confusion today, on a fix that was already correct and already
verified. It is not obviously a bug (a reader's text should be stable), but it
means *any* archive-side correction — the cleansing pass above especially —
lands only for readings chosen after it ships.
