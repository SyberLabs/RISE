*Written after the mobile threshold work shipped and SOL's Experience Program
phases 1–4 were committed (`0fb9c2b`). This sequences what is actually open,
says why in that order, and names what is deliberately not in it.*

## The shape of it

Four phases, in dependency order, plus a parked list. The ordering principle is
simple and worth stating once: **repair what everything else is measured with,
then spend the session on the one item that unblocks the most, then take the
highest-leverage single unlock, then build the thing we actually want.**

## Phase 0 — Ground the instruments

**Rationale.** The unit runner now crashes its worker pool outright
(`ERR_IPC_CHANNEL_CLOSED`) and only `--no-file-parallelism` yields a trustworthy
tally; `recitation.spec.js › an uncovered reading is read silently rather than
stalled` fails under full-suite load and passes 3/3 alone. Neither is a product
fault. Both mean the thing we verify with is less reliable than the thing we are
verifying, and this session is about to add a persistence format, a media type
and a sandbox — three areas where a false green is expensive.

**0.1 — Make the unit suite survive itself.**
Configure the pool in `vitest.config` rather than relying on a flag nobody will
remember. 109 files and 1477 tests is the new floor; it will keep growing.

**0.2 — Stabilise or quarantine the recitation flake.**
Find the timing assumption. If it cannot be made deterministic this session,
quarantine it *by name and with the reason written down* — a skipped test whose
skip is unexplained is the same failure as an inert guard.

**0.3 — The lifecycle round-trip suite.**
The cheap alternative to the virtual-clock kernel, named when that kernel was
deferred: assert that every identity-carrying config field — `visualProgram`,
`sourced`, `focal`, `atriumCollections`, and now the canonical Experience
Program — **survives or dies correctly** across persist → restore → reset.

This would have caught the entire Matthew-27 bug class. It is also the natural
place to *formally close* that item: `deserializeVisualProgram` is now in
`ChamberOrbital`, so SOL's fix appears landed, and this suite is how we prove it
rather than assume it.

**Exit:** one command, no flags, green, with the round-trip suite in it.

## Phase 1 — The Page paginates

**Rationale.** It is the largest unlock available and the only item on the list
that other work is explicitly waiting behind.

**1.1 — Pagination**, per `docs/vision/PAGE-MODE-SPEC.md`. Page Mode was always
intended to paginate; the current Page is one continuous column, which is also
why the whole reading's overhead lands at once instead of in divisible chunks.

**1.2 — Turn on procedural figures.** Already built and tested —
`pageCollectionId` and `sampleWorkEngine` in `work-engines.js`, the Chamber's
resolver branch — and held behind one constant, `PROCEDURAL_FIGURES` in
`flow.js`. Per `EXPERIENCE-PROGRAM-SPEC.md` §12 this was deferred *specifically
until the Page paginates*, so it lands here and costs almost nothing.

**1.3 — Projection is not carried through persistence** (red-team #11). A
restored session forgets whether it was a page or a stream.

**1.4 — Print output depends on scroll position** (red-team #12). Figures
hydrate lazily via `IntersectionObserver` in `PageReader.js`, so printing before
scrolling omits every figure never brought into view. Any fix must force-hydrate
before print. Note for whoever writes the test: this same property is why a test
counting `.page-figure img` must scroll first or it undercounts — it has already
cost real debugging time once.

**Not in this phase:** the Journey's Page support, which **already landed**. The
Page now reads a Journey's authored program; the Homeric movement's museum works
reach the page.

## Phase 2 — The Stream's pause boundary

**Correction, 2026-08-04.** This was filed under "Page Mode open threads" and it
is a **Stream** question — Gallery is a continuous field behind the reading
stream. It appeared in the Page notes only because it surfaced during that
hardening pass.

**The rule is decided:** an authored program **pins** the imagery to the
reading, an unauthored pool does not. So pausing halts the gallery when a
`visualProgram` is driving it — otherwise the imagery plays ahead of the text
and then runs out of hydration — and lets it drift for procedural and general
collections, where it is ambient and has no claim on any particular passage.

This is the same bound/unbound distinction `cueForAtom` already encodes, which
is the argument for it: no new vocabulary, one existing question asked in one
more place.

Small, decided, and it closes a deferral rather than opening one.

## Phase 3 — Experience Program, steps 5 → 7

Per `docs/vision/EXPERIENCE-PROGRAM-SPEC.md` §build-order. Steps 1–4 shipped in
`0fb9c2b`.

**3.1 — Step 5: MP4 as a first-class visual asset.** The spec already draws the
line and it should be honoured exactly: MP4 **as an imported media object**
belongs in the Workshop today; **exporting a program as MP4** is a
rendering/distribution pipeline and stays deferred by the North Star. Only the
first half is in scope.

**3.2 — Step 6: export/import Experience Program JSON.** The single
highest-leverage item on the whole list — the spec's own words are that this
*"alone enables the Live Curator."* The format is now canonical, strict and
immutable, so this is a boundary to open, not a design to invent.

**3.3 — Live Curator API documentation.** Follows 3.2 immediately: the moment
the format can leave the building, the contract for it has to be written down.

**3.4 — Step 7: formalise engine registry scope.** Small on its own, and it is
Phase 4's prerequisite, so it lands at the end of this phase rather than the
start of the next.

**Deliberately deferred:** step 8, the declarative Procedural Recipe format. It
is real work with its own design surface, it sits between "parameterised native
engines" and "never unrestricted same-origin JavaScript" on the spec's security
ladder, and RISE Chain does not need it to begin.
