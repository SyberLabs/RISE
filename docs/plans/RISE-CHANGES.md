# RISE Changes — the shared contract (coordinator, 2026-10-14)

RISE Changes turns what merged into RISE into a narrated RISE reading. Pilot: one digest a week for the TEAM (internal audience), from merged pull requests on SyberLabs/RISE. Readers-facing digests come later, behind a human approval; the schema carries `audience` now so that is additive.

## Flow
1. GitHub Actions workflow `.github/workflows/changes-digest.yml` (weekly, Monday 09:00 UTC, plus `workflow_dispatch` with inputs `since` (ISO date, optional), `dry_run` (boolean) and `supersede` (a published digest id, optional)).
2. `scripts/changes/digest.mjs` collects merged PRs since the newest digest's `period.to` (or 7 days back), routes them (a Jev-style finite-choice decision), composes one `rise.current.v2` with Claude, admits it with RISE's own validators, and writes two files.
3. The files are committed to the orphan data branch `changes-data` (NOT main; only main is protected). Nothing deploys.
4. The Worker serves them same-origin at `/content/changes/<file>` by proxying `https://raw.githubusercontent.com/SyberLabs/RISE/changes-data/<file>` (the repo is public).
5. The app shows `/changes` (the list) and `/changes/<id>` (the reading, its sources, and how each change was routed). The list says only what the page itself re-checks in every digest it shows, RISE's or a listed team's (`digestProblems` and the scene and SVG admission): it cites only the included pull requests and its pictures are safe to show. It also says the digest does not check that any change works. It once said only "RISE checks it before showing it", which reads as the claims being checked. The RISE Changes v2 Phase 0 study, 2026-11-06 (decision D10), classified every check as description fidelity, rendering and legibility, or safety; its functional-truth column is empty, since no check reads code, a diff, a test, a check run or a deploy. Numbers and legibility are not claimed because the number rule runs only when a digest is composed, against pull request text the page never has (until SVC-012 it also compared digits only and admitted the period's day, month and year anywhere), and illustrator code scenes, which RISE's own run allows, get no legibility check; v2 is to close the second.
6. The workflow opens one issue per digest ("What changed in RISE: <period>") linking https://rise.syberlabs.io/changes/<id>, with the routing table, so the owner is notified.

## Files on `changes-data`
`index.json`:
```json
{ "schema": "syberlabs.changes-index/v1",
  "digests": [ { "id": "2026-10-19", "audience": "team", "title": "…", "period": { "from": "2026-10-12T09:00:00Z", "to": "2026-10-19T09:00:00Z" }, "count": 12 } ] }
```
newest first, at most 200 entries. An entry may carry `"supersededBy": "<id>"`, a listed digest that re-ran its period (`--supersede`, below): `/changes` lists that one in its place, and the superseded digest's page links to it. It is optional, so every index written before it stays valid.

`<id>.json` where id matches `^\d{4}-\d{2}-\d{2}(-[a-z0-9]{1,8})?$` (date of `period.to`, a short suffix only if two runs share a day):
```json
{ "schema": "syberlabs.changes-digest/v1",
  "id": "2026-10-19",
  "audience": "team",
  "title": "What changed in RISE, 12–19 October",
  "period": { "from": "ISO-8601", "to": "ISO-8601" },
  "generatedAt": "ISO-8601",
  "model": { "router": "claude-sonnet-5-5", "composer": "claude-sonnet-5-5", "via": "Claude Code" },
  "changes": [
    { "number": 652, "title": "…", "url": "https://github.com/SyberLabs/RISE/pull/652", "mergedAt": "ISO-8601", "mergeSha": "2f13e80a…(40 hex)",
      "route": { "audience": "skip|team|readers|both", "significance": "minor|notable|major", "kind": "feature|fix|performance|design|infrastructure|records" },
      "included": true, "reason": "routed|records-only|limit|unspoken|unrouted" } ],
  "current": { "schema": "rise.current.v2", "...": "an admitted Current" },
  "sources": { "0": [652], "3": [653, 656] },
  "quality": { "firstPass": false, "repairs": { "composition": 1, "illustrator": 2 }, "checks": { "process-talk": 1, "text-crosses-shape": 2 },
               "density": { "pictures": 6, "includedChanges": 8, "speakingBeats": 17, "pictured": 17, "longestUnpictured": 0 } }
}
```
- `reason` `unspoken`: a change routed into the reading that no beat spoke of; the run leaves it out (`included: false`) and says so in `notes`, rather than repairing the composition.
- `reason` `unrouted`: a change whose router answer was not admitted (Route, below); it keeps the fallback route `skip/minor/records` and is never included.
- `sources` maps a beat index (string) of `current.beats` to the PR numbers that beat speaks about; every number must be in `changes` with `included: true`; every included change is cited by at least one beat.
- `quality` (optional, before `notes`): the run's first-pass score (Quality gates, below). `firstPass` is true only when nothing was repaired and nothing let go; `repairs` counts the repair requests of each stage; `checks` maps each rule that fired (a lower-case id, at most 40 of them) to how many times. Every digest the pipeline writes has it; the two written before it do not, and stay valid. `density` (optional; the digests written before it have none) measures the finished reading: the pictures it shows, the included changes it speaks of, its speaking beats (beats with refs), how many of them are shown a picture of what they speak of, and the longest run of speaking beats without one.
- `notes` (optional, last): 1 to 20 sentences of at most 300 characters saying what the run let go, such as a picture not drawn; absent when there is none.
- `current.origin` = `{ kind: "model", name: "<composer model>", provider: "Anthropic, via Claude Code" }` (check the Current schema's origin fields and keep within them).
- Bounds: at most 60 changes listed, at most 24 included; titles ≤ 200 chars; the whole file ≤ 256 KB.

`cache/routes/<mergeSha>.json`, one per pull request the router routed, named by its merge commit (Route, below):
```json
{ "schema": "syberlabs.changes-route/v1", "mergeSha": "2f13e80a…(40 hex)",
  "route": { "audience": "team", "significance": "notable", "kind": "fix" },
  "contract": "(64 hex)", "at": "ISO-8601" }
```
`contract` is the sha256 of the router's system text, the router's model id (so moving the router to another model reroutes everything), the route context's version (`ROUTE_CONTEXT_VERSION` in `scripts/changes/route-context.js`) and the fact rules' version (`FACTS_VERSION` in `src/core/changes/facts.js`, bumped whenever a fact rule the router reads changes). The run writes these files to its out directory; the workflow commits them with the digest, never on a dry run. A file is replaced whenever the run could not use it (Route cache, below), so a stale or broken one is rewritten by the next run that routes its pull request. The Worker does not serve them (its filename rule admits the digest and index names only) and the app never reads them. The published digest format is unchanged.

## Trust
- Everything in these files is model-written or PR-written. The app admits `current` through the SAME admission a card's Current goes through (scene code and SVG admission, the Current validator) before playing, and validates the envelope against this schema; a file that fails is shown as "This digest could not be shown", never played. The app's check requires each pull-request URL to be this repository's. A digest written for another repository fails that check, and the Worker does not fetch one.
- Every run, including the weekly one, asks GitHub whether the repository is public and stops before reading an index, a pull request, or a model when it is not. A name that is not `owner/name` stops before that request. The error repeats nothing GitHub returned.
- `.github/workflows/changes-public.yml` is the run another public repository calls on its own runner, pinned to a commit of this file. It checks out that commit of RISE, never the caller's dependencies. The repository is `github.repository` and is not an input. `--figures kit` refuses an illustrator brief, so the run writes kit figures and no scene code. The model credential is the caller's secret. The issue links to the file on the caller's `changes-data` branch. RISE does not fetch that branch.
- The Worker proxies only filenames matching `^index\.json$|^\d{4}-\d{2}-\d{2}(-[a-z0-9]{1,8})?\.json$`, GET/HEAD only, returns `application/json`, `X-Content-Type-Options: nosniff`, caches index 5 minutes and dated files a day (they are immutable once written, but a re-run may replace one).

## The generator (PR A), as built
These refine the contract above. The code is in two places. `src/core/changes/` holds the pure pieces the app may share, which import nothing from the live layer: `contract.js`, the envelope check both sides use (`digestProblems`, `indexProblems`, `sourcesProblems`), with `collect.js`, `prefilter.js`, `write.js`, `claude-cli.js` and the sample in `fixtures/`. `scripts/changes/` holds the Node pipeline that reaches the live layer (the host guide, the MCP size bound): `route.js`, `compose.js`, `admit.js` and `run-digest.js`, which `digest.mjs` runs.

- **Run.** `node scripts/changes/digest.mjs [--since <ISO>] [--out <dir>] [--dry-run] [--supersede <id>] [--figures kit] [--repo owner/name] [--cache <dir>] [--claims]` (`--claims`: Claims, below). It reads GitHub through `gh` and writes `<id>.json`, `index.json`, `issue.json` and `run.json` to a new or empty out directory, with `cache/routes/<mergeSha>.json` for each route the router gave this run, and `rejected.json` whenever RISE refused a model answer, rewritten whole at each refusal so a run that fails, times out or is cancelled still leaves every answer refused so far (a run that refused nothing writes none). `rejected.json` is a JSON array, one entry per refused answer in the order refused: `{ stage, attempt, beat?, refusal, answer, truncated? }`, where `stage` is `composition`, `illustrator` (with the picture's `beat`; a figure the rendered check refused, and an answer let go as a cue, count too) or `router` (only when a route in its answer could not be read: the first answer, whose unread pull requests are asked once more, and the retry's, whose still unread ones take the fallback route, the `unrouted` case), `refusal` is the lines RISE refused it with, and `answer` is the model's raw text. The prompt is never kept (the code and the public pull requests rebuild it), and the answer is the one `claude-cli.js` returns, from which any echo of the model credential is already redacted. Each answer is cut at 65,536 characters (the largest Current RISE admits) and the file at 4 MiB, an entry cut so marked `truncated`. Why: the Phase 0 audit could not label two refusals (L02 and L27) because only the refusal lines reached the Actions log and the answers were gone. Both workflows upload `run.json` and `rejected.json` as the run's artifact (`if: always()`, kept 90 days, `continue-on-error` so a failed upload never skips the commit; the public workflow's lands in the calling repository); neither is ever committed to `changes-data` or served, since the commit step copies only `<id>.json`, `index.json` and the `cache/routes/` files. The repository is public, so any signed-in GitHub user can download the artifact: everything in it must come from public pull requests or RISE's own code, and nothing else may be added to it. `--cache <dir>` is a copy of the data branch to read cached routes from (locally and in tests, any directory with the same layout); both workflows check `changes-data` out read-only for it before the run, with `persist-credentials: false`, so no credential is kept in that checkout, and pass it only when the branch exists. It never commits, pushes or opens an issue; the workflow does, and skips both on a dry run. `--repo` defaults to SyberLabs/RISE. `--figures kit` is the public-repository mode: a brief is refused and repaired like any other composition fault, and a scene with code is not written.
- **Period.** From the newest `period.to` in `index.json` on `changes-data` (or seven days back, or `--since`) to the moment of the run; a pull request is in it when merged after `from` and at or before `to`. With `--supersede <id>`, the period starts at that digest's `period.from` unless `--since` is given.
- **Supersede.** `--supersede <id>` (the workflow's `supersede` input) re-runs a published digest's period when the one published falls short (the 2026-10-16 digest showed 2 pictures in 19 beats). The new digest takes the day's next id (`-2`, as any second run that day), and the index marks the old entry `supersededBy` the new id; the old file is never touched, so its address still answers and links to the new one. A digest the index does not list, or one already superseded, is refused before any model is asked; supersede the newest instead. A superseding run reads the route cache like any run, so every pull request the first digest routed keeps its route and only those merged since are routed: the supersede 2026-10-16-2 asked the router again and dropped #685 and #693, routed minor that time.
- **Collect.** GraphQL `repository.pullRequests(baseRefName: "main", states: MERGED)`, newest-updated first, paged until a pull request was last updated at or before `from`. Kept: number, title (one line, at most 200 characters), body (first 4,000 characters, for the models only, never written), url, mergedAt, merge commit, labels, the first 100 changed paths and the file count. The same query, paged the same way, also asks for what a fact card reads: the pull request's added and deleted lines, each of the first 100 files' added and deleted lines, the first line of each of the first 100 commit messages (one line, at most 200 characters; `messageHeadline` is not used because GitHub cuts it near 70 characters with an ellipsis), and the number and title of the first 10 issues it closes (`closingIssuesReferences`). Kept beside the cut body: the whole body up to 65,536 characters (`LIMITS.fullBody`), cut there with `bodyCut: true` so a pathological body cannot blow a model call, for the models only and never written. GitHub's schema makes every line count non-null, so a node without one fails the run (`#n: no line counts`) rather than reading as 0, a plausible count a later page would publish unchecked. A page GitHub answers with HTTP 502 or 504 is asked for once more at half the size (25), since the heavier query may time out on a large week; a second failure fails the run. Fields as documented for [PullRequest](https://docs.github.com/en/graphql/reference/objects#pullrequest), [PullRequestChangedFile](https://docs.github.com/en/graphql/reference/objects#pullrequestchangedfile), [PullRequestCommit](https://docs.github.com/en/graphql/reference/objects#pullrequestcommit) and [Commit](https://docs.github.com/en/graphql/reference/objects#commit); cost as reported by [`rateLimit`](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api). Measured 2026-11-06 with `gh api graphql` on one page of 50 (#712 to #770): 2 points and 373,537 bytes, against 1 point and 202,784 bytes before. Not asked for, though the v2 plan listed them, because no Phase 1 or 2 stage reads them and on the recorded week they say nothing about the change: the review summary (no approval and no unresolved thread on any of #651 to #671, since the main ruleset requires every thread resolved and no approval) and the head commit's check runs (11 of those 21 show a failed check that is not `CI`, a Pages rule outside the change, while `CI` passed on all 21; a page that showed it would imply a functional verdict the digest never makes). With both added, the same page answered HTTP 502 on its one try.
- **Fact cards.** `factCard(pull)` in `src/core/changes/facts.js` turns one collected pull request into `{ number, mergeSha, title, body, bodyCut, labels, commits, files: [{ path, additions, deletions }], fileCount, additions, deletions, areas: [{ area, files, additions, deletions }], flags: { migration, config, dependency, workflow, docsOnly, testsOnly }, issues: [{ number, title }] }`, by code with no model. `body` and `bodyCut` are collect's whole body and cut; the body is for the model stages only and never written to a published file (in the recorded week #655's "Not verified" starts past the 4,000-character cut the composer still gets). An area is a directory: the first, or the first two under `src/` and `scripts/`, with `.` for a file at the root; areas are listed by changed lines, most first. Flags are path rules: `dependency` is a package manifest or lockfile at any depth (npm, Yarn, pnpm and Bun: `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`; Go: `go.mod`, `go.sum`; Rust: `Cargo.toml`, `Cargo.lock`; Python: `pyproject.toml`, `poetry.lock`, `requirements.txt`, `Pipfile.lock`; Ruby: `Gemfile`, `Gemfile.lock`; PHP: `composer.json`, `composer.lock`), `workflow` is under `.github/workflows/`, `migration` is in a `migration` or `migrations` directory or a `.sql` file, `config` is a `*.config.*`, `.env*` or `wrangler*` file, `docsOnly` is every file under `docs/` and `testsOnly` every file a `.test.` or `.spec.` file or under `e2e/`; the two only-flags are false when more files changed than were listed. The plan's `schema` and `publicApi` flags are left out: no path rule says which files are a schema or a public interface. Contributor text on the card (body, commit subjects, issue titles) is raw data, quoted where a prompt is built. The router reads the cards (Route, below); the composer is sent what it was before (a test pins the keys of each pull request it is sent, and that #655's composer body stops at the cut), and the recorded week's digest is unchanged byte for byte.
- **Records only.** Every changed file under `docs/product/tasks/`, and every changed file seen (a pull request with more than 100 files is never records-only). Listed with route `skip/minor/records`, never offered to a model.
- **Route.** One call for the pull requests not cached; the answer is `{"routes": {"<number>": {"audience", "significance", "kind"}}}`. The router is shown each pull request's fact card through its context contract (`routeContext` in `scripts/changes/route-context.js`): number, title, labels, the whole pull request's file count and added and deleted lines (areas cover only the first 100 files collect lists, and a 400-file sweep must not read as 100), areas with their files and added and deleted lines, the names of the flags set, and the first 600 characters of the body, quoted as data with `<` escaped. It replaced a 1,500-character body excerpt and the first 30 paths: on the recorded week the router's input fell from 33,279 to 20,514 bytes (system text included; 33,279 is `buildRouteRequest` at 58c3448c on the recorded week's candidates), and the 2026-11-02 run (41505796959) had sent it 56,641 by the Phase 0 context inventory. A test pins the contract's fields and that size, so a field added fails it. Each pull request's answer must have exactly the three keys, each one of the menu's values. The pull requests whose answer could not be read are asked once more, in one call holding only them; a pull request still unread gets `skip/minor/records`, stays listed, and is written with reason `unrouted`, never `routed`, so a format slip is not mistaken for the router's choice (#760's skip in the 2026-11-02 digest could not be told apart from one). The run log counts the unrouted pull requests when there are any, the issue says how many under its table, and a run where every answer fell back says so as its reason for writing nothing. Answers for pull requests not offered are ignored.
- **Route cache.** Before asking the router, the run reads `cache/routes/<mergeSha>.json` (Files on `changes-data`, above) for each pull request, and uses a cached route only when the file is exactly that shape, names that merge, carries the current contract hash, and its route admits under the current menu; anything else (not JSON, another merge, a stale contract, an off-menu value, an extra key) is ignored, said in the run log, and routed afresh. A file over 4,096 bytes, or one reached through a link anywhere below the `--cache` directory, is read as absent and not logged, and is routed afresh the same way. The files sit on a public branch, so nothing else in one is trusted. Each route the router gives is written as a cache file, replacing one the run could not use; an unrouted answer is never cached. The run log says how many router calls were made, the retry counted among them, and how many routes came from the cache. A re-run over the same period makes none when the first run wrote its digest (only a written, non-dry run's cache files are committed) and nothing in it was unrouted. To clear a cached route, delete its file on `changes-data`; to clear them all, bump `ROUTE_CONTEXT_VERSION`. A route stays as first given, so a route a pull request's text steered is kept, not resampled away, until it is cleared. Why: routing was a sample, not a decision. At one commit over the same 24 pull requests, two runs routed 5 differently, 7 pull requests flipped between included and left out across runs, and the supersede 2026-10-16-2 silently dropped #685 and #693 (RISE Changes v2 Phase 0 study, 2026-11-06). A second run now reads the first's routes.
- **Select.** Included in the team digest: any audience but `skip` (`team`, `readers` or `both`) with significance `notable` or `major`; the team hears everything that matters, and each change keeps its routed audience for a later readers digest. At most 24, majors first then the newest (`limit` for the rest). Listed: at most 60, every included one, then every `unrouted` one that fits (the page shows those listed; the issue counts every one and says how many are not listed), then the weightiest and newest of the rest, records last. `changes` is written newest merge first. `count` in the index is the number of included changes.
- **Compose.** One call, taught by `CURRENT_GUIDE` from `src/live/guide/` (unchanged). The included pull requests, and as context only the routed ones left out (marked `"included": false`, never spoken of or cited, since a later minor fix may settle an included change's caveat), are given in merge order with their merge times; the composer is told that a later pull request may resolve or supersede an earlier one's caveat (unverified, pending, left to decide), to state such a caveat only when no later pull request resolves it, and to speak as RISE in plain words with no flourish; the close says the week's last fact and stops, with no summary or slogan. The answer is `{"current", "pictures", "opening"?, "close"?}`. RISE's engines are named only in `opening` and `close`, each `{ engine, params? }`: the pipeline places the opening on the first beat and the close on the last and declares their scenes (`opening`, `close`). A scene in the Current or a picture that names an engine is refused before anything else is checked, in plain words: "RISE's engines open and close a digest; a change is shown with a kit picture" (the rule `engine`). So an engine in the middle of the reading cannot be written at all; it is no longer repaired (dry run 38696304051 repaired a third engine at beat 16). Each beat carries its own `refs`, the pull requests it speaks about, beside its words; the pipeline takes them off the beats and writes the contract's `sources` from them (a separate map drifted from the beats it named: dry run 38666483992 repaired one). Each theme gets one picture, on its first beat, held across its beats: a kit figure `{ beat, refs, kit: { kind, ... } }` whenever the change is a measurement, a sequence, a sorting, a layout, a set of rules or a before and after (a rule or a process change is a `list` or a `compare`; The figure kit, below), or, for a diagram no kit kind can express and at most 2 a digest, a brief `{ beat, refs, medium, brief }` for RISE's illustrator (the brief 20 to 300 characters naming every label and number to draw, medium `figure` by default or `scene` when motion explains). The composer is shown one compact example of each kind (`KIT_EXAMPLES` in `compose.js`) and each slot's budget in characters, written from the kit's own measure (`KIT_BUDGETS` in `figure-kit.js`, the same geometry and average character its refusals count with), so the guidance cannot drift from what the kit accepts; a test holds the prompt's numbers to the kit's (dry run 38879838950 repaired a list title one budget over). A picture's `refs` are the pull requests it shows and must be among its beat's refs, so a picture sits on the beat that speaks of it (dry run 38688524786 showed #668's frame rates on a beat about #652); its numbers, kit values and figure text alike, must be stated by the pull requests it cites, not anywhere in the week. A picture must show something the words alone do not. An included change no beat cites is no longer refused: the run marks it `unspoken` (above), and the first-pass score counts it as a check that fired (`unspoken`) and as something let go, so the first pass is lost, though nothing is repaired; more than five share one note. `current.origin` is set to `{ kind: "model", name: <composer model>, provider: "Anthropic, via Claude Code" }` whatever the model wrote.
- **Admit.** The connector door's checks (65,536-byte bound, `validateRiseCurrent`, `admitSceneCode`, `admitSvg`, refusals worded by `describeDiagnostic`), the `sources` rules worded for `refs` (a ref to a change not included, or an included change in no beat's refs, is refused as before), `figureProblems` for every kit figure (its sentences prefixed `"pictures"[n].kit:`), and one more, the number rule: every number a beat says or shows must be stated by the number, title or body of a pull request in that beat's own refs (a beat that cites none states none), a picture's by the pull requests it cites, the title's by the pull requests some beat cites (an included one no beat cites leaves the reading as unspoken), and the drawn figures' by an included one; a kit figure's labels and values are held to it too (a bar's `max`, a scale never printed, is not). A beat's refusal names its refs and, when another included pull request states the number, that one: `beat 2 (refs [653]) says "700", which none of them states; #652 states it: cite #652 on this beat if it speaks of that change, or say it without a number`. Numbers are compared by exact value only: `22k`, `22,000` and `22 thousand` are one number, `1.50` is `1.5`, `09` is `9`, and a comma separates thousands only before groups of three digits (`1,5` is two numbers); a unit never converts, so `1.5 s` and `1,500 ms` stay two numbers. A number written in words is a number: one to ninety-nine, compounds with hundred, thousand and million (`twenty-four`, `seven hundred and fifty`, `a thousand`), and `one and a half`. "one" is not read where it is not a count: `one of` names a member of a group (the group's size, as in `one of three`, is still read); after no, this, that, each, any, every, the or which it is a pronoun (`no one`, `the one that changed`); joined by a hyphen to a word that is not a number it is part of that word (`one-time`, `one-line`). `one more release` and `one service` are counts. A literal is one whole token: a version (`v2`, `2.1.287`, so `2.1` is not stated by `2.1.287`) and a capitalised identifier (`LIVE-035`, `RDR-030`, so `(LIVE-035)` in a title does not state `35 models`). A word is read as a number only from the rule's own word lists, never from a name every object has (`constructor`). A day, month or year of the period's two dates passes only in that role inside a date, never as a count: a day before a month name (`30 October`, `30th October`, `30th of October`); a day after one (`October 30`, `Oct. 30`, `October 30th, 2026`) only where the date ends, at punctuation or the end of the text, or in a range whose second day ends there (`October 23 to 30.`); the first day of a range whose second day stands before a month name (`12 to 19 October`); a year after a month name or such a day; and an ISO date. So `30 percent` in a week ending 30 October is refused and `30 October` passes; `In October 26 readings were added` and `by October 26 and 2 new texts` read 26 and 2 as counts; `on 30 October, 23 readings` in a week from 23 October reads 23 as a count. Why: the 2026-11-02 run spent its last repair refusing a figure's `22000` for #765's `22k lines` (the Phase 0 study's only number refusal, a false positive), while a beat could take its number from any pull request of the week and the rule admitted a fabricated `twelve`, `v2` in a period ending on the 2nd and `26 readings` in one starting on the 26th (study part 3, section 7.1). One number is stated for every beat whatever its refs: the count of included changes some beat cites (in any of the rule's spellings), only where it counts changes: directly before `change`, `pull request`, `PR` or `update` (singular or plural), optionally after more, new, separate, distinct or included, read where the number stands (`Two changes this week` passes; `Two services were added`, or `Two services were added across two changes`, beside two cited changes that state no 2 is refused), since the host computes it and the composer cannot fabricate it; an included change no beat cites is not counted, because it leaves the reading, so "Three changes" cannot stand beside two spoken ones. No other count is stated (not the listed count, not a count per kind), and the title is not given it. The coordinating agent admitted this count on 2026-11-06, and reported it to the owner, for 2026-10-26's opening beat, "Two changes this week", which cites no pull request and was the one published beat the scoped rule refused; refusing such counts would cost repairs on later weeks. All seven published digests admit under this rule with their own pull requests: `src/core/changes/fixtures/published-digests.json` holds their titles, periods, beats with refs, and included pull requests (number, title, body cut at 4,000 characters, as read on 2026-11-06), and `admit.test.js` reads them offline. An ordinal outside a date is read as its number (`the 30th release` needs a 30). Still not read: `half`, `twice`, `dozen`, and ordinals in words; digits grouped by spaces and decimal commas are not normalized; a date in a pull request's own text states its numbers like any other. A refusal gets a repair call with the refusal's lines, then one more; a third refusal fails the run without writing.
- **The composition rule** (admitted with the composition, its refusals repaired like any other): the composer's Current declares no engine, so the engines are at most the 2 RISE placed, at the opening and the close, for mood; every picture is a kit figure or a brief (at most 2 briefs), at least one, at most as many as the Current's 8 scenes leave beside the opening and the close, each on a beat that names no scene of its own (never the first beat under an opening or the last under a close); no engine is held for more than 4 beats, and no picture for more than 6 while every beat under it cites one of its changes (4 when a beat under it has no refs). The first real digest (run 38635708731) held one attractor through all 16 beats; this rule is why it cannot happen again. When the pictures need more scenes than the opening and the close leave, RISE gives up the close, then the opening, as long as that makes room (the run log says so); otherwise both stay and the room is refused. The 8 scenes and the beat limits are the connector's and are unchanged.

No more than 2 speaking beats in a row may go unpictured, and every included change routed `major` that a beat speaks of must be in some picture's refs. ## Claims
The claims stage (SVC-014, RISE Changes v2 Phase 1) lists what each included pull request claims, every claim resting on exact words of the pull request, so that a later stage can put the source beside every sentence it writes. In this phase it runs only with `--claims` and in the replay, and the composer is not given its output (Phase 2).

- **Why.** The composer reads the first 4,000 characters of a body, and authors put what they did not verify at the end. In 12 of the 101 pull requests the seven published digests list, the caveat section starts past that cut: #652, #653, #655, #660, #672, #673, #684, #686, #732, #738, #742 and #746 (`docs/plans/changes-v2/study/03-false-negatives.md`, section 5, on the `changes-study` branch). A thirteenth, #734, whose "Known limits" starts at character 4,283, was found by the claims stage's own detector on 2026-11-06 and missed by that Phase 0 audit, whose list of headings did not include known limits. #655's "Not verified" says that whether a model resolves "it" from the block is unverified; the 2026-10-14 and 2026-10-15 digests said it can be understood. The claims stage reads the whole body and must quote such a section.
- **Request.** `buildClaimsRequest(card)` in `scripts/changes/claims-context.js`, one call per pull request: the stable system text first (`CLAIMS_SYSTEM`), then the pull request quoted as data with `<` escaped (`quoted` in `route.js`): its title, labels, areas with their files and added and deleted lines, the names of the flags set, the whole body (collect's, up to 65,536 characters, line endings read as LF), the commit subjects and the closed issues' numbers and titles. A test pins the fields and #655's request at 8,329 bytes, system text included, so a field added fails it.
- **Answer.** `{"claims": [{"text", "kind", "status", "quote", "field", "index"?}]}`: `text` the claim in plain words; `kind` one of behavior, performance, interface, security, process, docs; `status` one of shipped, flagged (merged but switched off, unverified or uncertain), partial, reverted, pending (not done, left for later, or awaiting a person); `quote` the exact words the claim rests on; `field` body, title, commit or issue; `index` the commit's or issue's position in its list, from 0. The model gives words, never offsets, because a model cannot count characters; code computes the span.
- **Admission** (`admitClaims` in `scripts/changes/claims.js`, by code, no model). The quote must occur word for word in the field it names, both read with line endings as LF and nothing else normalized; the quote must occur there exactly once (a quote found twice is refused, `its quote occurs 2 times in the body; quote enough words to be found once`, so a span cannot anchor outside the section it was quoted from), and the span is that occurrence, `{ field, index?, start, end, text }`, in code points (the unit `LIMITS.fullBody` counts). Every number in the claim's text must be in the quote, read by the number rule's own reader (`mentionsIn` in `admit.js`): `22k` and `22,000` are one number, a number in words is a number, a unit never converts. Kind, status and field come from `CLAIM_MENU` (`src/core/changes/contract.js`); at most 12 claims (the entries past the twelfth are dropped, in one line), each text at most 300 characters and each quote at most 1,000; a claim with another shape, or one repeating an earlier claim's span, is dropped. Each dropped claim is listed with its reason, never repaired by guess (a claim dropped for a number gets the number repair, below, from the model). The claim id is `cl_` and the first 12 hex of sha256(`<repo>#<pr>@<mergeSha>:<field>:<index or empty>:<start>-<end>`).
- **Caveat rule.** `caveatSections(body)` finds a caveat section by code: a Markdown heading, or a label line (a line wholly in bold, or a line of at most 80 characters ending in a colon that is not a list item, a quote, a table row or a heading), whose text names one of `CAVEAT_PHRASES`, whole words in any case: not verified, unverified, not done, not yet, not in this PR, pending, awaiting, human gate, needs a human, TODO or TODOs, known limit, limits, limitation or limitations. A bold label followed by its colon (`**Not verified**:`) is a label line too; no line inside a fenced code block (``` or ~~~) is a heading, so a `# TODO` in a shell snippet neither makes a section nor cuts one short. The detector is linear in the body. "Not in this PR" (#684, #732) and "Human gate" (#738) are on the list because those are the headings three of the 13 use. The section is the text under the line up to the next heading of its level or higher (a label line's, up to the next heading or label line); a heading with nothing under it is none. The list finds a section past the cut in all 13, tested on their bodies recorded on 2026-11-06 (`src/core/changes/fixtures/hidden-caveats.json`), and in the recorded week finds exactly #652, #653, #655, #660 and #661 (whose "Not done or seen" is inside the first 4,000 characters). Over the 88 distinct candidates of the seven periods it finds a section in 20 bodies: the 13, and seven whose section is inside the cut (#661, #674, #712, #719, #759, #761, #766). Each section must be overlapped by the body span of an admitted claim of status pending or flagged. When one is not, or the answer cannot be read, or it admits no claim, the pull request gets one repair call: its own request, its previous answer quoted as data (`<previous_answer>`, with `<` escaped) and the refusal lines, which name each unquoted section by its offsets and its heading JSON-quoted with `<` escaped and cut to 80 characters, at most five of them and then how many more. The repair's answer replaces the first only when it admits at least one claim and leaves no more sections unquoted than the first; otherwise the first is kept. A section still unquoted leaves the claims kept and the gap recorded (`gap` on the result and the cache file, a line in the run log); code never writes a claim. A call that fails leaves that pull request without claims, says so in the log, and the others go on.
- **Number repair.** Why: the Phase 1 exit replay (run 42316694794) admitted 579 claims and dropped 148, and 141 of the 148 were dropped because the claim's text states a number its own quote does not hold (`its text says "120", which its quote does not`), mostly a true number written elsewhere in the pull request: content lost, not fabrication (the other 7 quoted words not in the field). One span per claim stays (`docs/plans/changes-v2/SCHEMA-V2.md` on the `changes-study` branch), so the stage asks for a wider quote rather than a second one. When an answer drops claims for a number, the repair lists them after the refusal lines, quoted as data (`<dropped_for_a_number>`, JSON with `<` escaped: each claim's place in the answer, its text, quote, field and index), and asks for each either a wider quote copied exactly from the same field that holds every number in its text, or the same claim without the number. An answer holds at most 12 claims, so the list is at most 12. **The rule: a pull request makes at most two claims calls.** The repair is one call: when the first answer also needs the caveat repair (a section unquoted, unreadable, or nothing admitted), the list is folded into that repair, which asks for the whole JSON object again and is taken by the caveat rule above; otherwise it asks only for the listed claims, and each one admitted at a span not already admitted is added to the first answer's claims (within the 12-claim limit, never replacing one). Either way every claim passes the same admission, so no claim is admitted without each of its numbers in its quote, a repair that keeps the number on the same narrow quote is refused again, a duplicate of an existing span is refused, and the caveat coverage is recomputed from the claims kept. A repair that cannot be read or admits nothing changes nothing; a claim the repair still drops is not asked about a third time. `recovered`, on each result, in `claims.json` and per pull request and in all in the replay's `report.json`, counts the claims the repair admitted at spans the first answer did not (a folded repair's new pending claim counts too; a pull request read from the cache counts 0). The repair's wording is part of the claims contract, so `CLAIMS_CONTEXT_VERSION` is 2 and no claim cached under version 1 is reused. Tested with a fake model on #660 (a wider quote holding "120" recovers it), #672 (the claim without "2.1.287" is admitted) and #686 (a repair keeping "18" on the same quote is refused), three of the replay's dropped claims rebuilt on their recorded bodies.
- **Cache.** `cache/claims/<mergeSha>.json`: `{ schema: "syberlabs.changes-claims-cache/v1", mergeSha, contract, claims, gap, at }`, `contract` the sha256 of the claims system text, the model id, `CLAIMS_CONTEXT_VERSION` and `FACTS_VERSION` (`contractHash`, as for routes). A file is read through the route cache's `cacheReader` (a 40-hex name, at most 128 KiB, never through a link), its shape held to `cachedClaimsProblems`, then every claim admitted again from its own span against the pull request's current text and required to equal the claim filed, and `gap` to be the gap they leave; anything else is ignored, said in the run log, and claimed afresh, so a body edited after its merge is claimed again. A result is cached when it admits at least one claim, a gap included (marked); never when its answer could not be read or nothing admitted. The digest workflow does not commit these files yet.
- **`--claims`.** After routing, the run claims its included pull requests only, four calls at a time, and writes `claims.json` (`{ repo, model, contract, calls, repairs, pulls: [{ number, mergeSha, fromCache, claims, dropped, caveats: [{ heading, start, end, covered }], gap, recovered }] }`) and the new claims cache files to the out directory; an answer that needed a repair is kept in `rejected.json` with stage `claims` and its `pull`. Without the flag the run is unchanged: a test pins that it makes exactly the router, composer and illustrator calls it made before and returns the same keys.
- **Replay.** `node scripts/changes/replay.mjs --periods <file|builtin> --cache <dir> --out <dir>` asks GitHub whether the repository is public, then runs collect, fact cards, route (with the route cache) and claims over each period, reading routes and claims from `<cache>/cache/` and writing each new one there, so a second replay with the same cache makes no model call for a pull request the first cached (tested with a fake model). Each pull request a stage asks the model about is counted once a stage in `report.json`: in `cachedReCalls` when its cache file was there when the replay started (a cache that did not hold), else in `uncachedRetries` (on a second pass, a pull request the first could not cache because its call failed or admitted nothing). `builtin` is the committed list of the seven published periods (`src/core/changes/fixtures/replay-set.json`, with the 13 hidden-caveat pull requests and its source), not `index.json` read live: the exit test's set stays fixed when later digests or supersedes change the index, and reading it needs no network. Each period's included pull requests are claimed, and so is each hidden-caveat pull request merged in it, included or not, so the caveat check never depends on a route. It prints and writes `report.json` to a new or empty out directory: per pull request its claims, per period and per run the model calls by role, the input and output bytes, the cache hits, the claims a repair recovered (`recovered`, per pull request and in all), and for each hidden-caveat pull request whether a pending or flagged claim quotes its section. `.github/workflows/changes-replay.yml`, dispatched by hand only (never on a pull request, never required, `contents: read` and `pull-requests: read`, the digest job's reads), installs Node 22.23.3 and Claude Code CLI 2.1.287 as the digest job does, replays twice with one cache, fails when the second pass's `cachedReCalls` is not 0 (its `uncachedRetries` are reported, not failed), and keeps both reports as an artifact for 30 days.

## Quality gates
Every failure seen in a real run becomes a mechanical check that answers with a plain sentence a repair can act on; a sentence in a prompt alone drifts. The checks are pure (`src/core/quality/`, nothing from the live layer) and are run by the digest pipeline and, count only, by the connector.

| Seen in a run | The check |
|---|---|
| A label drawn across its box (dry run 1, "harmonograph") | `svgLayoutProblems`: `text-crosses-shape` |
| A closing line about "the next dry run" (two dry runs) | `processTalkProblems`: `process-talk` |
| A number no pull request states | the number rule (Admit, above) |
| One visual held through the whole reading (run 38635708731) | the composition rule (above), and `pictureCadence` at the connector |

**`svgLayoutProblems(svg, { roomWidth = 390, ground = '#0a0a0f', maxWork })`** reads the figure with the tokenizer that admits it (`svgTree` in `src/core/svg-admission.js`; a figure admission refuses is not judged) and answers `{ problems: [{ rule, line, message }], notes, work }`. Each label is a box: its x, y, dx and dy, font-size (16 when none is set), text-anchor, dominant-baseline and textLength, under every ancestor translate, scale and axis-aligned matrix. Its width is Helvetica's advance for each character (Arial's are the same), 0.56 em for a character outside that table, 0.6 em in a monospace family, 8% more when bold; a flat 0.56 em per character was tried first and wrongly refused two published labels made of narrow letters. Its height is the em box, 0.8 em above the baseline and 0.2 em below. The rules:
- `text-overlap`: two label boxes meet.
- `text-crosses-shape`: a label straddles the edge of a rect, circle or ellipse (their bounding boxes), or touches a line, polyline, polygon or path (their segments, a curve as eight chords, absolute and relative commands alike; the bounding box of a connector is not ink). A stroke widens the edge by half its width, and a label keeps 0.05 em clear of it.
- `text-outside`: any part of a label outside the viewBox.
- `text-too-small`: font-size × scale × 390 / viewBox width under 12 pixels.
- `text-low-contrast`: the label's fill (its attribute, its style, its parent's, `currentColor` as the words' ink `#eef0ff`, black when nothing sets one), blended by its opacity, under 4.5:1 (WCAG) against the ground, or against a filled rect it sits wholly on.
What it cannot place it never guesses: a rotation or skew, a CSS transform, a `<style>` sheet, an arc, a `<use>`, a `<textPath>`, a nested `<svg>`, a list of positions, a line placed by y alone and a length in another unit are each skipped with a note. At most ten problems a figure. `work` is the comparisons it made; past `maxWork` it compares nothing and says so.

**`processTalkProblems(texts, { subject })`** finds a beat that speaks of the making instead of the change, from a small literal list: dry run; test, trial or practice run; this, next, later, future, following, previous or last run; will show or will tell followed by nothing, in, whether, if, once, after, when, soon or later ("the room will show the picture" passes); remains to be seen; a later, next, coming, future, final, pending or human review, and under review; as of writing; the pipeline, unless the pull requests speak of a pipeline. A phrase an included pull request says itself passes.

**`pictureCadence(current)`** is `{ beats, scenes, longestHold }`: the beats, the distinct scenes they start, and the longest run of beats under one picture (a v1 Current by its segments' visuals).

In the pipeline:
- **Composition.** `admitComposition` holds the beats to `processTalkProblems` with the included pull requests as the subject; a hit is a refusal line like any other, repaired in the same two repairs. Each refusal also says how many lines each rule gave.
- **Illustration.** Every figure the illustrator draws is held to `svgLayoutProblems` as part of its admission, so a problem goes back as a diagnostic (`line N (text-crosses-shape): the text "…" at x 72, y 206 crosses the edge of the <rect> on line 11 …`) within the same three attempts. A code scene has no static text to place: it keeps the number rule only.
- **Rendered check.** `scripts/changes/render-check.mjs` draws each admitted figure in Playwright's Chromium, fitted whole into 390 × 844 and 1440 × 900 on the room's ground with `#eef0ff` as its `currentColor`, and measures every label with `getBoundingClientRect`: `rendered-overlap` (two labels' glyph boxes, less a tenth top and bottom for the font's leading, meet by more than a pixel), `rendered-outside` (a label past the figure's edge) and `rendered-too-small` (under 12 pixels at 390). The page has JavaScript off, a policy that loads nothing, and every request refused. A figure at fault goes back to the illustrator once, as a refusal carrying its source; a repaired figure still at fault is let go like a refused one (its beat keeps the scene before it, and `notes` says why). One browser serves the run and starts with the first figure; each check takes about 10 ms after a start of about 1.3 s (measured on 24 real figures). The weekly job installs it with `npx playwright install --with-deps chromium`, the build the lockfile pins. Its test, `scripts/changes/render-check.test.js`, needs that browser: the full unit suite runs it (`full-validation.yml` installs Chromium), and the fast set the required `CI` check runs excludes it (`vitest.fast.config.js`).
- **The score.** Every rule that fired and every repair asked for is counted into `quality` (`createTally` in `run-digest.js`). The run log prints `Quality: First pass: no — 3 repairs (1 composition, 2 illustrator); checks fired: figure (3), process-talk (2)` and the object as JSON; the issue carries the same line, and `/changes/<id>` shows it under "How this was chosen". `quality.density` is measured on the finished reading (`measureDensity`), so a picture let go counts against it: the log, the issue and the page carry one more line, `Pictures: 6 for 8 changes; every speaking beat pictured`, or `Pictures: 2 for 8 changes; 6 of 17 speaking beats pictured, at most 8 in a row without one`. A first pass is worth nothing if it is bought with an empty reading: the two are read together.

At the connector (`worker/mcp-quality.mjs`), count only: after the door admits a Current and its answer is built, one log line `{"event":"rise.quality","rules":{"<rule>":<count>},"beats":n,"scenes":n,"longestHold":n}`, rule ids and counts only, never text or SVG. Nothing the connector accepts, refuses or answers changes, and a test holds every response byte-identical with and without it. It never throws. It reads at most 16 KB of figure text and makes at most 50,000 comparisons a Current; a figure past either bound is counted as `unchecked`. Measured in Node: 1.5 ms for the published digest's Current (six figures, 9 KB), at most about 4 ms for the worst Currents built to the bounds. Workers Logs keeps the line (`observability.enabled` in `wrangler.production.jsonc`).
